# rumil_parsers benchmarks

JSON parser micro-benchmarks for `rumil_parsers`. Generated by
`tool/bench/json_bench.dart`. Three workloads:

- **integer_heavy** — 50k-element list of integers.
- **float_heavy** — 50k-element list of floats with a fractional part.
- **mixed** — 50k records with int / string / bool fields.

Each measurement is the median of 100 runs (one warmup discarded).
Wall clock in milliseconds. Lower is better.

## 0.7.0 → 0.8.0

Workstation: Linux x86_64. Dart SDK 3.11.4. Each pass ran separately
on a quiet system (no other interactive workloads competing for the
CPU). AOT via `dart compile exe`; Wasm via `dart compile wasm` invoked
through Deno's `WebAssembly.compile`.

### AOT

| Workload       | Input  | 0.7.0 (ms) | 0.8.0 (ms) | Speedup | μs/byte |
|----------------|-------:|-----------:|-----------:|--------:|--------:|
| integer_heavy  | 282 KB |     158.5  |     149.4  |  1.06×  |  0.517  |
| float_heavy    | 380 KB |     183.8  |     173.7  |  1.06×  |  0.447  |
| mixed          | 2.75 MB|    1343    |    1087    |  1.24×  |  0.377  |

### Wasm

| Workload       | Input  | 0.7.0 (ms) | 0.8.0 (ms) | Speedup | μs/byte |
|----------------|-------:|-----------:|-----------:|--------:|--------:|
| integer_heavy  | 282 KB |      83.3  |      65.2  |  1.28×  |  0.226  |
| float_heavy    | 380 KB |      92.6  |      74.2  |  1.25×  |  0.191  |
| mixed          | 2.75 MB|     593.5  |     425.4  |  1.40×  |  0.148  |

The `μs/byte` column normalizes the 0.8.0 wall-clock by input size.
Despite the larger absolute time, **mixed is the fastest workload per
byte** — the new capture-based string parser handles `"user_NNNN"`
fields in one substring slice, and the integer-shaped `id` / `score`
fields take the JsonInt fast track without the `int.tryParse + double
fallback` machinery integer_heavy pays on every token. The absolute
mixed time is ~10× the integer_heavy time because the input is ~10×
larger (200k value nodes plus 50k JsonObject allocations vs 50k
JsonInt allocations for integer_heavy).

The Wasm column carries the larger relative wins. The JsonInt /
JsonDouble split lets dart2wasm specialize integer-vs-float code paths
through the parser pipeline (i64 vs f64 separation), which the
flattened `JsonNumber(double)` representation in 0.7.0 forced into a
single homogeneous f64 path. The capture-based number and string
parsers compound the effect: fewer intermediate allocations means
fewer Wasm GC interactions per token.

The mixed workload sees the biggest relative speedup (1.40× Wasm)
because it composes every optimization in this release at once: the
JsonInt/JsonDouble split (id, score), capture-based numbers,
capture-based strings (name), and the `_lex` cleanup at every token
boundary. integer_heavy and float_heavy each exercise only a subset.

The AOT column is more modest because Dart's AOT pipeline already
specializes well on monomorphic call sites; the absolute numbers were
never the headline. The win surfaces under Wasm's stricter type-flow
story.

## Reproducing

```bash
# AOT
dart compile exe tool/bench/json_bench.dart -o /tmp/json_bench.aot
/tmp/json_bench.aot --runs 101 --platform aot

# Wasm (requires Deno or another JS host that can call
# WebAssembly.compile on a dart2wasm output)
dart compile wasm tool/bench/json_bench.dart -o /tmp/json_bench.wasm
deno run --allow-read run_bench_wasm.mjs /tmp/json_bench.wasm \
  --runs 101 --platform wasm
```

The `--runs N` flag controls the run count (first run discarded as
warmup; pass `101` for 100 measured runs). The `--platform LABEL` flag
tags the JSON output for later ingestion. Use the same workstation
and a quiet system to compare across versions; do not run multiple
passes in parallel.
